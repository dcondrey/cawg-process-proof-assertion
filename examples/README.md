# Examples and verification boundaries

These examples serve two different purposes. Neither is a conforming implementation of the proposed process-evidence profile.

## Proposed envelope

`inline.cbor` and `external.cbor` exercise the proposed CDDL. Their `.display.json` companions show byte strings as `{"hex": "..."}` for inspection; that display format is not the wire encoding.

The inline example covers the exact UTF-8 bytes `A short example.\n`. Its payload says `Illustrative bytes, not a process proof.` The profile URI uses the reserved example.org domain. The external example has a placeholder assertion digest and no resolving manifest. They are schema examples, not valid process evidence, real profiles, or C2PA manifests. A verifier must not report successful process verification for either.

Run the checks with the installed `cddl` validator (checked with 0.10.5) and uv. The script uses `cddl --ci` so a rejected case has a failing exit status:

```sh
uv run --locked examples/check.py
```

The checks cover both envelope alternatives, required nested fields, byte-string and integer types, digest lengths, context and string limits, version rejection, unsupported fields/mappings, and the inline-size boundary. They also reject the existing WritersProof application assertion as an instance of the new schema. Unexpected validator failures are not counted as successful rejection tests. Committed envelope files must match their complete generated bytes, so a valid prefix with extra bytes is not accepted as the fixture.

These are schema and fixture checks. They do not implement a general CBOR wire validator or enforce duplicate-key rejection, URI semantics, cryptographic validity, profile support, content mapping, freshness or privacy. The specification's verification rules remain obligations for future implementations.

To intentionally regenerate the illustrative envelope bytes and display files:

```sh
uv run --locked examples/check.py --write-examples
```

## Existing WritersProof fixture

`writersproof/document.txt` is copied unchanged from the committed producer fixture in WritersProof revision `c8962052df50398846bf8c2cea66aeff5d9fd590`. Its source and SHA-256 digests are in `writersproof/source.json`. The corresponding producer is `crates/cpoe-protocol/tests/text_proof_block_fixture.rs` at that revision. It uses a public synthetic test signing key and has zero captured checkpoints. The prose, action description and `humanCreation` declaration are test data, not evidence that a human wrote it.

`writersproof/manifest.c2pa` is the base64-decoded manifest from that document. No application code or captured user document was changed. The independent reader report was produced on 9 November 2026 with c2patool 0.26.68:

```sh
c2patool examples/writersproof/manifest.c2pa --detailed
```

| Check | Observed result |
|---|---|
| Direct read of the armored `.txt` | This c2patool build reports `Unsupported file type`. |
| Standalone manifest signature and assertion hashes | Individual checks report success. |
| Overall standalone manifest result | `Invalid`, including `claim.malformed` (claim box label), `signingCredential.untrusted`, and `assertion.dataHash.mismatch`. |
| Document content binding | The standalone read has no corresponding document and reports an exclusion beyond the data length. `check.py` separately recomputes the declared SHA-256 over the covered 189 document bytes and confirms the match. Modified or appended covered text fails that comparison. This does not cure the other manifest failures. |
| Process assertion | Version 2, `evidenceId` and `evidenceHash`; not the proposed envelope. |
| Process evidence payload | Not supplied in this fixture. Its digest cannot be independently checked here. |
| Captured checkpoints | Zero. No writing-process or human-authorship conclusion follows. |

`reader-report.json` preserves the observed failures rather than normalizing them away. `check.py` checks that retained report and the fixture digests; it does not rerun the reader or independently verify its signatures. Use the command above for a fresh reader run. Reader versions and local trust policies may affect those results.

The example exposes a practical interoperability gap: parsing a signed application assertion does not tell a reader how to obtain and validate its underlying evidence or what content/process guarantees it supports. It also exposes separate enclosing-format issues. A new process profile does not fix those issues by itself.

## ECHO

The proposal's ECHO discussion was checked against the r8 research draft, its vector manifest, security model and WritersProof capture-contract notes. Its reviewed checkout is based on commit `cbb11afb4d442cdd096c89e1bd8ab7a0f5e6ea48` with ongoing draft edits. It is not a pinned public profile release. No ECHO code, private history or proof fixture is distributed here, and no ECHO security or benchmark result was reproduced for this documentation change.

A future ECHO interoperability package needs a public immutable profile revision, proof/public-input vectors, complete independent verification, rejection cases, and the explicit security qualifications described in the draft. A successful schema check cannot substitute for those requirements.
